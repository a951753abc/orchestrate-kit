# 測試變慢診斷

適用：全套測試或某一層測試耗時過長、逐次變長，或要求「加速測試」。測試節奏（當前任務的 focused 測試當下跑；耗時的慢層在 push 前或由 CI 執行）以專案的測試規定為準，本檔只寫診斷步驟。

## 1. 先讀既有紀錄，不先重跑

- 從測試入口的耗時紀錄、runner 的 console log（vitest、Pest、pytest 預設會印逐檔毫秒數）、JUnit／JSON 報告取逐檔耗時，記下指令原文、filter、並行設定與 exit code。
- 平行執行時，整套時間由最慢的 worker 決定，逐檔耗時不能相加成整套時間；先找出決定總時間的那幾個檔。
- 列出多次執行的趨勢（例：1343 秒 → 1815 秒），確認是逐次變長還是突然變長；突然變長照本 skill 流程 1 的「釘首見時間＋變更清單」處理。
- 既有紀錄已足以回答時，不另外量測。

## 2. 拆開耗時來源

對佔大部分時間的少數檔，最小量測一條代表性測試，把時間拆成：

- 建測資（fixture、seed、release 建置、外部程序啟動）
- 測試本體（Act 與 Assert）
- 環境（資料庫 migration、瀏覽器啟動、登入、`sleep` 等待、平行時的資源爭用）

臨時計時一律加本 skill 的唯一前綴，收尾 grep 清除。

## 3. 評估加速方案前，先查不變條件

- 共用或快取測資前，先查產品有沒有綁定測資的不變條件：依賴指紋、雜湊、簽章、作者與覆核紀錄、過期判定。不變條件涵蓋的檔案每張任務都會改時，快取每次都失效，省不到時間。
- 測試若斷言「流程實際跑過」的產物（收據、trace、執行次數），用 builder 直接產生結果等於偽造證據；這類測試只能縮短流程本身，例如平行化或減少重複建置。
- 多條測試共用同一份測資前，逐條確認差異是否為斷言重點；共用後讓斷言描述的 Given 沒有實際使用，屬語意改動，交使用者裁決。

## 4. 方案排序

1. 分層：把慢檔移到慢層，改在 push 前或由 CI 執行（不改測試內容，最先可做）。
2. 不改斷言的加速：fixture 內部平行化、拆檔讓 runner 分給不同 worker、前置狀態改走 API 或 fixture 而不走 UI。先量測並行上限再決定並行數。
3. 改測試設計（共用測資、減少建置份數）：涉及斷言語意時交使用者裁決。

## 輸出

沿用本 skill 的輸出格式；Observed facts 要列：佔大部分時間的檔與其耗時、各耗時來源的秒數與量測方式、查到的不變條件與程式位置。
