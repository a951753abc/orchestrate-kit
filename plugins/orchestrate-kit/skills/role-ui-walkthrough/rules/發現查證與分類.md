# Rule 1 - 每項發現列入前要開截圖確認

- Level: `MUST`
- agent 的回報與逐步紀錄是線索，不是證據。列入主控筆記的每項發現，都要有人用 Read 開過它引用的截圖；圖上看不到的事不寫。
- agent 會看錯小字，也會抄錯字元。回報裡的畫面文字、網址、數字一律以截圖為準。（實例：把「備記」讀成「備註」；把連結裡的大寫 I 抄成小寫 l。）
- 截圖數量多時，主控親自看關鍵的那些（卡住的步驟、列為阻擋的項目、agent 回報彼此矛盾的地方），其餘交給產出文件的 agent 在引用前開圖。主控筆記寫明哪些圖是主控親自看過的。
- 開圖後與回報不符時，照實寫「截圖上看不到：〈哪一句〉」並把那一句從事實拿掉，不自行改寫成別的說法。

# Rule 2 - 「沒有出現」類的發現要看兩張截圖並查程式

- Level: `MUST`
- 「沒有成功訊息」「沒有結果畫面」「沒有通知」這類發現，要同時看該步的 `NNNa.png`（動作後 0.3 秒）與 `NNN.png`（動作後 2 秒），兩張都沒有才成立。
- 截圖間隔仍可能錯過短暫的畫面。列為阻擋之前，請唯讀 agent 查前端的處理函式：成功後有沒有顯示訊息、有沒有停留時間、有沒有重新讀取資料。
- 程式有、截圖沒截到的，改記為「存在但停留時間短」或排除，並寫進排除紀錄。

## Good Example

```md
- 事實：按「通過」後沒有結果訊息。014a 與 014 兩張都只有清單少了一列。
- 程式：`resources/js/pages/admin/HostReview.tsx:88` 成功後只呼叫 `reload()`，沒有 toast。
```

## Bad Example

- 只憑 agent 的一句回報就列入；實際上完成畫面存在，顯示 2 秒後跳轉，agent 在 2.5 秒後才截圖。

```md
- 事實：付款後沒有結果畫面（agent 回報）。
```

# Rule 3 - 先對照既有裁定，定案的設計不當成問題

- Level: `MUST`
- 每項發現在列入前，對照專案的決策紀錄、規格、已知限制清單、UX 盤點與既有的自動檢查項目。查證 agent 對每項回報下列其一，並附檔案路徑、行號與照抄的原文：
  - 就是要這樣（定案的設計）
  - 已知問題、尚未處理
  - 已接受的限制
  - 只是相關、沒有直接裁定
  - 查無（列出搜尋過的關鍵字）
- 定案的設計：不列為待裁項目；畫面與裁定不一致時才列，並寫明是哪一條裁定。
- 已知問題與已接受的限制：列入時引用原紀錄，不重新當成新發現。
- 文件之間彼此不一致（例：Roadmap 與規格說法不同）時，另列一行「文件之間的不一致」，交使用者裁定，不自行選邊。
- 查證 agent 只回報文件裡真的有的文字，不判斷該不該修、不提改善建議。

# Rule 4 - 程式依據由唯讀 agent 取得，主控抽查

- Level: `MUST`
- 對「畫面值與資料對不上」「動作後沒有更新」「某個入口只在某一頁」這類發現，請唯讀 agent 找出程式依據：檔案路徑、行號、照抄關鍵的 1～5 行，加一兩句事實說明。沒查到的部分寫明搜尋過的關鍵字。
- 給查證 agent 的任務說明寫的是畫面觀察到的事實與要回答的問題，不寫猜測的原因。
- 主控抽查引用（開檔核對行號與原文），抽查的處數與結果寫進主控筆記。
- 查證 agent 不提修法。

# Rule 5 - 排除的回報要留紀錄

- Level: `MUST`
- 被排除的回報寫進主控筆記的判讀限制，一項一句，含排除原因。常見原因：
  - 看錯字。
  - 短暫畫面沒截到（程式有）。
  - 測試資料造成（例：測試信箱特別長，欄位顯示不完整）。
  - 攔截的固定回應造成。
  - 定案的設計。
- 排除紀錄讓讀者知道某件事有被看到並判斷過。

# Rule 6 - 每一段的狀態只用這五種

- Level: `MUST`

| 狀態 | 定義 |
| --- | --- |
| 做得完 | 沒有停下、沒有連續不符，畫面回答了該回答的問題 |
| 做得完，有阻礙 | 做完了，但過程中有入口要猜、說明不足、要重新整理、點錯等情形 |
| 卡住後做得完 | 曾經回報卡住（連續 3 次不符或找不到入口），沒給提示或給了提示後做完；註明有沒有用到提示 |
| 看得到結果但資訊不足 | 動作完成，但 agent 回答不出「畫面有沒有告訴你」的問題，或畫面沒有標示來源、時間、對象 |
| 做不完 | 給了提示仍做不完，或畫面上沒有這個功能的入口 |

- 每段附一句話依據與截圖範圍（`<run> NNN–NNN`）。
- 受事先知識影響的段落（agent 自述用到任務說明以外的知識）在依據裡註明。

# Rule 7 - 每項發現標收尾關係

- Level: `MUST`

| 收尾關係 | 定義 |
| --- | --- |
| 阻擋 | 命中不合格條件，交給真實使用者之前要處理 |
| 範圍須明文 | 要先裁定範圍或做法，才寫得出規格或動得了工 |
| 可另案 | 不影響走完一趟，可以分批處理 |

- 不合格條件以專案自己的 UX 判準為準。專案沒有時用這四條：主要任務沒有提示就做不完；狀態誤導或動作後沒有回饋；填過的內容消失；在目標裝置上操作不了。
- 只有工程上判斷得出做法的項目才標「阻擋」並附工程視角建議。產品行為的選擇（要不要通知、要顯示什麼）標「範圍須明文」，列出選項與事實，不代為裁定。

# Rule 8 - 每項發現標修改類別

- Level: `MUST`

| 修改類別 | 適用情形 | 修改時的做法 |
| --- | --- | --- |
| 規格＋測試 | 會改到系統存什麼、通知誰、誰能做什麼 | 先寫短規格與後端測試，掛決策編號 |
| 畫面直接改 | 只有畫面與文字 | 改完看截圖；既有 e2e 斷言到的文字一起更新 |
| 診斷後修 | 畫面值與資料對不上 | 先依 orchestrate-kit:debug-by-evidence 取得證據再修 |
| 自動檢查 | 程式判定得出、容易再犯 | 修改時一併加進 lint 或既有的 UX 自動檢查 |

- 一項可以同時屬於兩類（例：狀態的來源屬「規格＋測試」，文字屬「畫面直接改」），分開寫。
- 「沒有提示就做不完」這類發現無法用自動檢查守住，修改後以同一段重跑角色 agent 驗證。
- 專案有自己的開發方式（規格格式、測試框架、檢查指令）時，類別名稱後面接專案的實際做法。

# Rule 9 - 發現分群後才編號

- Level: `SHOULD`
- 同一個原因造成的多個現象合併成一項（例：七個動作成功後都沒有結果訊息，合成一項並列出七處）。
- 分群依修改時會一起處理的範圍：系統行為、資料與顯示對不上、動作後的回饋與畫面更新、入口與操作流程、文字與用語、版面。群組用字母、項目用字母加序號（A1、B3）。
- 每項的固定欄位：一句話標題、收尾關係、修改類別、事實、截圖（`<run>/<步驟>`）、程式（有查才寫）、既有裁定與紀錄、要裁定的事（可另案且無待裁時寫「沒有待裁定的事」）。

# Rule 10 - 判讀限制逐條寫明

- Level: `MUST`
- 主控筆記的判讀限制至少回答這五件事：
  - 事先知識：agent 自述開始前知道哪些事；有沒有任何一條描述畫面長相；哪些段落受影響。
  - 看錯字：已確認的實例。
  - 範圍：這次只看了旅程經過的畫面；沒有操作的功能逐項列出。
  - 資料：測試帳號、攔截的固定回應、資料庫內容的來源。
  - 查證：哪些截圖主控親自看過；程式引用抽查了幾處。
- 這些限制要出現在現況表與裁決報告的證據基準說明。
