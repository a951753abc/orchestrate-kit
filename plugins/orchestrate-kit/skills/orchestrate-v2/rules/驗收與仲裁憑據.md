# Rule 1 - 完成、修好、通過的憑據是 orchestrator 親自讀過的原始輸出

- Level: `MUST`
- 宣稱工單「完成／修好／通過」之前，orchestrator 必須親自讀過每條驗收的原始輸出，來源只有三種：
  - 自己執行的指令：讀終端的實際輸出。
  - 交給 `opus-lite-verifier` 的步驟：讀它依驗收清單存下的原始輸出檔，包括指令原文、exit code、完整 stdout／stderr、截圖與頁面快照。
  - executor 寫進工單證據檔目錄的證據檔：修改前的 `before-<驗收編號>.txt` 用來確認修改前的失敗或基準值，修改後的 `after-<驗收編號>.txt`（一次性操作為 `after-op.txt`）用來判定結果；兩種檔內都要有指令原文、exit code 與完整輸出（第一行 `$ <指令原文>`、下一行 `exit code: <n>`）。先執行 `uv run "${CLAUDE_SKILL_DIR}/scripts/check_evidence.py" --dir <證據檔目錄> --repo <專案目錄> --allow <允許檔>... --expect <本工單驗收編號，逗號分隔>`：`after-` 檔早於允許檔最後修改時間會標 `stale` 旗標；它印出的指令原文（多段時為最後一段的指令）、exit code 與末段原文算 orchestrator 親自讀過的原始輸出；有旗標、或預期結果需要末段以外的內容時讀整檔。`ok` 只表示證據檔格式完整、沒有旗標，不表示驗收通過；通過與否看 exit code 與末段原文。`stale` 只用來排除明顯過期的證據，不能證明跑的是新版程式；這部分接受 executor 紀錄的可信度。
- 採用範圍：低風險全部採用 executor 證據檔；中高風險也採用，只有涉及底線（會破壞資料、造成授權錯誤、或波及其他系統的問題，例：同一顆資料庫伺服器上其他系統的資料庫）的驗收項目由 orchestrator 自己重跑或寫進 verifier 清單。
- 證據檔只有摘要、`check_evidence.py` 標出 `no_command`、`no_exit_code`、`stale` 或 `missing_after` 旗標、摘要列出 `missing_evidence=<編號>`（`--expect` 列出的驗收編號沒有 `after-` 檔）、或來源不明時，該條自己補驗。
- `earlier_nonzero` 旗標（同一檔最後一段之前有非 0 的 exit code）：讀整檔，確認非 0 那段是預期結果（先紅後綠、預期失敗的檢查）才採用；確認不了就自己補驗。
- `final_nonzero` 旗標（`after-` 檔最後一段的 exit code 非 0）：讀整檔，確認非 0 是該條驗收的預期結果（例：預期失敗的檢查、`rg` 無命中回 1）才採用；不是預期結果即該條驗收失敗，確認不了就自己補驗。
- `decode_errors` 旗標（解碼出現替換字元，常見於 CP950 輸出）：讀整檔，確認判定所需的內容沒有落在亂碼處才採用；判定不了就自己補驗。
- 摘要列出 `missing_allow=<路徑>`（允許檔不存在，該次 `stale` 判斷不完整）：先確認 `--repo` 與 `--allow` 路徑後重跑 `check_evidence.py`；路徑無誤而檔案確實不存在時，比照 `stale` 自己補驗。
- executor 回報內的摘要與「已通過」、reviewer 或 subagent 轉述的「已通過」、verifier 回報裡的執行紀錄、摘要與任何判定、「理論上可行」的推論都不是憑據；它們只指出該去驗什麼。
- 驗收失敗就如實回報失敗與實際輸出，不美化、不改寫成「大致完成」。
- close 報告逐條標明驗收結果的來源：「通過（主控重跑）」（verifier 照清單執行的也算）、「通過（採 executor 證據）」或「未查證」；未查證的項目不寫成通過。填不出 `templates/close-report.md`「親自查核的測試證據」段的指令或證據檔與其輸出，就不能 close。

## Good Example

- 這個例子是好的，因為 orchestrator 沒有採信 executor 回報裡的「已通過」，自己跑 `check_evidence.py` 讀證據檔的指令原文、exit code 與末段原文，確認沒有 `stale` 等旗標、摘要沒有缺件，再依 exit=0 與末段的測試結果判定驗收通過並標明來源。

````md
executor 回報：V1 `npm test -- tests/csv/bom.spec.ts` 全綠，證據在 C:/tmp/evidence-wo2/。
$ uv run "${CLAUDE_SKILL_DIR}/scripts/check_evidence.py" --dir C:/tmp/evidence-wo2 --repo C:/work/shop --allow src/csv/parse.ts --allow tests/csv/bom.spec.ts --expect V1
after-V1.txt | exit=0 | runs=1 | ok
  cmd: npm test -- tests/csv/bom.spec.ts
  Tests: 1 passed, 1 total
files=1 flagged=0 skipped=0
→ 無旗標、無缺件；exit=0 且末段 1 passed → 工單 #2 V1 通過（採 executor 證據）。
````

- 這個例子也是好的，因為驗收含瀏覽器操作時交給 verifier 照清單執行，orchestrator 不看 verifier 的回報內容，讀產物檔原文後才判定。

````md
工單 #3 驗收含瀏覽器操作（上傳 BOM 開頭的 CSV 後檢查預覽表頭）→ 依驗收清單樣板寫清單，派 opus-lite-verifier。
verifier 回報：步驟 1〜4 已執行，產物在 C:/tmp/verify-wo3/。
orchestrator 讀產物檔：
- `01-bom-test.txt`：首行 `$ npm test -- tests/csv/bom.spec.ts`，末兩行 `Tests: 1 passed, 1 total`、`rc=0`
- `04-preview.png`：預覽表第一欄表頭顯示 `id`，前面沒有多出的空白或亂碼
→ 工單 #3 驗收通過。
````

- 這個例子也是好的，因為中高風險工單只把涉及底線的那條驗收留給 orchestrator 自己重跑，其餘沿用 executor 證據。

````md
工單 #4（中高風險：migration 會刪除過期訂單）
- V1 `npm test -- tests/migration/purge.spec.ts`：`check_evidence.py` 對 `after-V1.txt` 無旗標、exit=0，末段 `Tests: 3 passed, 3 total` → 通過（採 executor 證據）
- V2「刪除只含 `status = expired` 的列」涉及底線 → orchestrator 自己在複本重跑查詢，刪除列全為 `status = expired` → 通過（主控重跑）
````

## Bad Example

- 這個例子是壞的，因為它把 executor 的回報直接當成驗收結果，未親自確認就寫成「應該沒問題」；把 verifier 回報的「全部通過」當成驗收結果也是同一種錯；證據檔帶 `stale` 旗標（executor 跑完驗收後又改了允許檔）仍採用，等於拿過期證據判定。

````md
executor 說測試都過了、typecheck 也綠，看起來沒問題，工單 #2 算完成，進 review。
verifier 回報步驟 1〜4 全部通過，工單 #3 也算完成。
`after-V1.txt` 帶 `stale` 旗標（executor 跑完驗收後又改了 `parse.ts`），仍寫成「通過（採 executor 證據）」。
````

# Rule 2 - findings 依觸發分類決定查證力氣，結果依類別寫進 close 報告

- Level: `SHOULD`
- 先看 finding 的觸發分類（reviewer 標「正常使用可觸發」「特殊條件才觸發」或「不確定」；沒有標或依據不成立時自己判斷），再決定花多少力氣查證：
  - 特殊條件才觸發、且不涉及底線（定義見 Rule 1）→ 不親自重現，直接列為已知限制候選，交使用者決定接受或要求修正。
  - 正常使用可觸發、或涉及底線 → 親自查證：能親自重現（跑出失敗、或讀 code 指出確切的錯誤路徑）→ 真問題；重現不了但邏輯成立 → PLAUSIBLE，交使用者裁決，不硬判。
  - 標「不確定」→ 比照 PLAUSIBLE。
- 真問題依使用情境判斷要不要修：涉及底線的必修；其餘不修的列為已知限制候選，附影響與復原方法。純風格偏好、與本次工單目標無關的「順手改善」→ 否決並記錄理由。
- 經使用情境判斷要修的真問題，開新窄修正工單（SKILL Phase 6）；不修的真問題、未查證直接列為候選的 findings 進 close 報告「待人工判斷事項」表，類別填「已知限制」或「未查證 finding」，附可能影響與需要人工做的事。
- PLAUSIBLE 與標「不確定」的 findings 附已嘗試的重現方式與判斷依據，進同一張表，類別填「PLAUSIBLE」。
- 涉及底線的項目在表中狀態填「需先裁定」，使用者裁定前不 close。
- 否決的 findings 與理由寫進 close 報告「殘餘風險與仲裁紀錄」段。

## Good Example

- 這個例子是好的，因為每條 finding 先依觸發分類與是否涉及底線決定查證力氣，再依類別寫進 close 報告對應位置。

````md
F1（正常使用可觸發）：`calcRefundable()` 金額為 0 時回傳 NaN → 親自以 `node -e` 重現 → 真問題，開修正工單
F2（特殊條件才觸發：同一筆訂單兩個請求在 10 ms 內同時退款，可能重複扣款）：涉及底線 → 親自查證，本機無法模擬 concurrency，但 code 確無鎖 → PLAUSIBLE，「待人工判斷事項」表狀態填「需先裁定」
F3（特殊條件才觸發：CSV 超過 2 GB 時記憶體不足）：不涉及底線 → 不親自重現，列「未查證 finding」
F4（風格）：建議把 `refund.ts` 內 helper 改成 arrow function → 否決，理由記入「殘餘風險與仲裁紀錄」
````

## Bad Example

- 這個例子是壞的，因為該重現的沒重現、不必重現的花了力氣、涉及底線的沒交使用者：F4 風格建議也開成工單，涉及底線的 F2 跑不出來就當假陽性略過，不涉及底線的 F3 卻花一小時重現。

````md
F1、F4 都開工單改掉；F2 我這邊跑不出來，應該是假陽性，略過；F3 花一小時造 2 GB 檔案重現。
````
