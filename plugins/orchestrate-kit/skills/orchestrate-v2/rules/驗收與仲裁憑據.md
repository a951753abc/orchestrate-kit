# Rule 1 - 完成、修好、通過的唯一憑據是 orchestrator 親自執行並親眼看到的輸出

- Level: `MUST`
- 宣稱工單「完成／修好／通過」之前，orchestrator 必須親自執行每條驗收指令並讀實際輸出。
- executor 的完工報告、reviewer 或 subagent 轉述的「已通過」、「理論上可行」的推論都不是憑據；它們只指出該去驗什麼。
- 驗收失敗就如實回報失敗與實際輸出，不美化、不改寫成「大致完成」。
- 填不出 `templates/close-report.md`「親自執行的測試證據」段的指令與輸出，就不能 close。

## Good Example

- 這個例子是好的，因為 orchestrator 沒有採信 executor 的回報，自己重跑並貼出實際輸出後才判定驗收通過。

````md
executor 回報：`npm test -- tests/csv/bom.spec.ts` 全綠、`npm run typecheck` exit 0。
orchestrator 親自執行：
$ npm test -- tests/csv/bom.spec.ts
  ✓ strips BOM from first header (12 ms)
  Tests: 1 passed, 1 total
$ npm run typecheck; echo exit=$?
  exit=0
→ 工單 #2 驗收通過。
````

## Bad Example

- 這個例子是壞的，因為它把 executor 的回報直接當成驗收結果，未親自確認就寫成「應該沒問題」。

````md
executor 說測試都過了、typecheck 也綠，看起來沒問題，工單 #2 算完成，進 review。
````

# Rule 2 - findings 依能否親自重現分為真問題、PLAUSIBLE、否決

- Level: `SHOULD`
- 能親自重現（跑出失敗、或讀 code 指出確切的錯誤路徑）→ 真問題，開新窄工單。
- 重現不了但邏輯成立 → 標 PLAUSIBLE，附已嘗試的重現方式與判斷依據交使用者裁決；拿不準就明說不確定，不硬判真假。
- 純風格偏好、與本次工單目標無關的「順手改善」→ 否決並記錄理由；不因 reviewer 提了就開工單。
- 三類的分類依據都寫進 close 報告「殘餘風險與仲裁紀錄」段。

## Good Example

- 這個例子是好的，因為三條 findings 各自對應到重現結果，PLAUSIBLE 附了嘗試過的重現方式。

````md
F1（correctness）：`calcRefundable()` 金額為 0 時回傳 NaN → 親自以 `node -e` 重現 → 真問題，開工單 #6
F2（回歸）：並發退款可能重複扣款 → 本機無法模擬並發，但 code 確無鎖 → PLAUSIBLE，交使用者裁決
F3（風格）：建議把 `refund.ts` 內 helper 改成 arrow function → 與工單目標無關 → 否決，理由記入 close 報告
````

## Bad Example

- 這個例子是壞的，因為它未重現就全數採信，把風格建議也開成工單，並把重現不了的問題硬判為假陽性。

````md
reviewer 列了三條，F1、F3 都開工單改掉；F2 我這邊跑不出來，應該是假陽性，略過。
````
