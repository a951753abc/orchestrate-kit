# Rule 1 - 診斷、切工單、驗收的判定、仲裁、close 自己做；委派出去的是實作，以及驗收的機械執行

- Level: `SHOULD`
- orchestrator 負責最貴、最關鍵的判斷：診斷、切工單、驗收的判定、仲裁、close；這些不發派。
- 除黏合修改與 Rule 2 的主控自做工單外，orchestrator 不親自寫 code；實作交給 executor。
- 驗收含瀏覽器操作（登入、點擊、填表、截圖）時，寫驗收清單派 `opus-lite-verifier`（opus、low），照清單執行並保存原始輸出；瀏覽器驗收需要 Playwright MCP，沒有時把瀏覽器步驟交使用者執行。
- 驗收只有指令時不派 verifier，orchestrator 也不親自試跑或重跑：由 executor 在工單內執行，標「修改前要跑」的項目修改前後各跑一次、其餘只在修改後跑，指令原文、exit code、完整輸出寫進工單的證據檔目錄；orchestrator 讀證據檔判定。只有涉及底線的驗收項目、以及證據檔不符 `rules/驗收與仲裁憑據.md` Rule 1 條件的項目，才由 orchestrator 自己重跑或寫進 verifier 清單。
- 理由：主控親自跑指令最慢，2026-09-27 實測每步秒數約等於 1 秒加上每千個輸出 token 11 秒，主控每一步都先花思考 token。
- 通過與否一律由 orchestrator 自己讀原始輸出判定，verifier 只執行與存檔。
- 需要頂級模型的只有診斷與仲裁，那是 orchestrator 自己做的事，不發派。

## Good Example

- 這個例子是好的，因為 orchestrator 自己完成診斷後才發派，發派的是實作與驗收的機械執行，判斷留在自己手上；只有指令的驗收由 executor 寫證據檔，orchestrator 讀證據檔判定、不重跑。

````md
診斷（自己做）：讀 `src/auth/*`，確認 token 續期邏輯只在 `refresh.ts` 一處；影響範圍兩檔。
發派：工單 #1 給 opus-lite-executor，改 `refresh.ts` 與其測試。
驗收：工單 #1 要登入後截圖確認續期提示 → 寫驗收清單派 opus-lite-verifier；通知回來後自己讀測試輸出檔與截圖判定。
工單 #2 驗收只有 phpunit 與 typecheck → executor 寫證據檔，orchestrator 讀 `after-V1.txt`、`after-V2.txt` 判定，不重跑。
````

## Bad Example

- 這個例子是壞的，因為它把診斷外包給 subagent、把驗收判定交給 verifier，orchestrator 拿到的是轉述，不是自己讀 code 與原始輸出的判斷；只有指令的驗收在發派前後由 orchestrator 親自各跑一遍，花的是最慢的主控時間。

````md
Agent(general-purpose)：「幫我看看 auth 模組哪裡有問題，然後直接修好。」
Agent(opus-lite-verifier)：「把工單 #1 的驗收跑完，告訴我過了沒。」
orchestrator 發派前先把五條驗收親自跑一遍，executor 回報後又全部重跑一次。
````

# Rule 2 - 依難度路由 executor，model 與 effort 隨層級綁定

- Level: `SHOULD`
- 主控自己做：下列條件全部成立才適用，任一條件不成立就照下方路由派 executor：
  - 單一模組；
  - Phase 2 的 `gate_hits` 為空，且工單目標未命中語意類 gate；
  - 預估執行步數在 15 個工具呼叫以內（A/B 中 opus-lite-executor 的中位數為 9）；
  - 不需要與其他工單並行；
  - 不含瀏覽器驗收。
- 主控自做工單的處理：不寫工單檔、不跑 baseline snapshot 與 compare、不寫證據檔；標「修改前要跑」的驗收照樣先跑；驗收由主控親自執行，終端輸出即憑據（對應 `rules/驗收與仲裁憑據.md` Rule 1 的「自己執行的指令」）；仍屬所屬交付範圍，交付範圍最後照常分級與 review。
- 理由：2026-10-26 A/B，3 張歷史 opus-lite-executor 工單 × 2 種做法 × 各 2 次重播。主 loop 直接做：主控 5～16 步、1.6～4.1 分、3～20k output tokens，結果與 orchestrate 相同；orchestrate-v2（本版的證據檢查與 baseline hook 改版後）：主控 15～21 步加 executor、2.9～10.2 分、10～40k tokens。改版後每張小工單的主控步數中位數 14（改版前 10.5），其中 risk-grade 與 close 樣板固定花 9～11 步。
- 一般 coding 與機械型（範圍明確、單模組、中低複雜度；批次替換腳本、改名、單檔小修）→ `opus-lite-executor`（opus、low）。
- 高難度 coding（跨模組、concurrency／狀態機、需要深度推理）→ `opus-executor`（opus、high）。
- Phase 2 的 risk_signals 估算 `gate_hits` 非空（policy 所列路徑類 gate），或工單目標命中語意類 gate（core_business_rule 核心商業規則、concurrency／狀態機、data_safety 資料安全、cross_module_contract 跨模組介面）→ `opus-executor`，不看 diff 大小與其他判準。
- effort 寫在各 agent 定義檔，Agent tool 無法單次覆寫；要換強度就換層級。

## Good Example

- 這個例子是好的，因為它依難度特徵挑 executor，而不是一律派最強模型。

````md
工單 #1（改 DTO 欄位名、單檔、測試已覆蓋）→ opus-lite-executor
工單 #2（撮合引擎狀態機新增「部分成交」狀態，跨三個模組）→ opus-executor
工單 #3（只改兩個檔，risk_signals 估算 gate_hits 命中 migration）→ opus-executor
工單 #4（依替換表寫一支帶 count==1 斷言的腳本）→ opus-lite-executor
工單 #5（單一模組內修一則錯誤訊息與其測試、gate_hits 為空、預估 8 個工具呼叫、只有 phpunit 驗收）→ 主控自己做：回合內列出目標、允許檔、驗收條件，先跑修改前驗收，修改後親自跑驗收讀終端輸出判定
````

## Bad Example

- 這個例子是壞的，因為它把單檔改名也派 opus-executor，在不需深度推理的工作上花 high effort 的思考成本；第二行則是跨模組且命中 gate 的工單仍由主控自己做，跳過 baseline 與 executor 證據，不符合主控自做的條件。

````md
所有工單一律 opus-executor，比較保險。
工單 #6（改兩個模組的共用介面，gate_hits 命中 migration）改動不大，主控自己做比較快。
````

# Rule 3 - 搜尋與精讀派 `opus-lite-explorer`，路由用的自訂 agent 定義檔必宣告 model 與 effort

- Level: `SHOULD`
- 找檔案、追引用、精讀文件等唯讀工作派 `opus-lite-explorer`（opus、low），不派 Explore、general-purpose 等內建 agent。
- 內建 agent 沒有定義檔可宣告 effort，Agent tool 也沒有 effort 參數，實際會沿用 orchestrator 的 effort（subagent transcript 的每回合 effort 紀錄可查證）；無 model 行的 agent 也會繼承 orchestrator 的模型。
- 路由表內的自訂 agent（executor、explorer、verifier、reviewer）定義檔必宣告 `model` 與 `effort`。

## Good Example

- 這個例子是好的，因為唯讀搜尋派給定義檔已宣告 opus＋low 的 explorer。

````md
Agent(subagent_type: opus-lite-explorer)：「列出所有引用 `LegacyPricing` 的檔案。」
````

## Bad Example

- 這個例子是壞的，因為內建 Explore 帶了 model 也無法指定 effort，實際會跑 opus＋xhigh（沿用 orchestrator 的 effort），不是 low。

````md
Agent(subagent_type: Explore, model: opus)：「列出所有引用 `LegacyPricing` 的檔案。」
````

# Rule 4 - 發派前必有 baseline

- Level: `MUST`
- 任何 executor 寫入前必須有 baseline（working tree 的 dirty、staged、untracked 與各檔 hash），並保留 manifest 路徑到驗收。
- 發派 `opus-executor`／`opus-lite-executor` 時，plugin 內建的 PreToolUse hook（`scripts/baseline_hook.py`）從工單「專案目錄」行取 repo 自動 snapshot，以 additionalContext 回報 manifest 路徑；工單已有 `baseline manifest：<存在的 .json 路徑>` 行時，hook 沿用該 manifest、不另外 snapshot。hook 回報未自動 snapshot（不是 git repo）時，orchestrator 必須在驗收前手動執行 `scripts/baseline.py snapshot` 補上。
- hook 在 snapshot 或寫索引時失敗會擋下這次派工（`permissionDecision: deny`），executor 不會啟動：orchestrator 照擋下訊息手動執行 `scripts/baseline.py snapshot`，在工單加一行 `baseline manifest：<manifest 路徑>` 後重新發派。
- 沒有 baseline 就發派，Phase 4 無法判定越界修改與使用者原有修改是否被覆蓋，驗收不成立。

## Good Example

- 這個例子是好的，因為 hook 回報的 manifest 路徑被記下來，驗收時 compare 有基準。

````md
Agent(opus-lite-executor, 工單 #1)
→ additionalContext：baseline hook 已自動 snapshot：C:/Users/x/AppData/Local/Temp/claude-orchestrate/3f2a…/baseline-20260903T081500Z.json
（記入工單 #1 的「baseline manifest」欄）
````

## Bad Example

- 這個例子是壞的，因為 hook 已回報沒有 snapshot，orchestrator 沒有手動補，驗收時沒有基準可比對。

````md
Agent(opus-lite-executor, 工單 #1)
→ additionalContext：專案目錄不是 git repo，未自動 snapshot，請手動執行 baseline.py snapshot
（沒有手動補 snapshot，直接進 Phase 4 驗收）
````

# Rule 5 - Codex rescue 只在 Claude executor 失敗兩次或需要異質視角時觸發

- Level: `SHOULD`
- 觸發：Claude executor 同一工單失敗兩次、或明顯需要異質模型視角時，由 orchestrator 直接發派（不經 subagent）。
- 不作一般工單入口。
- Codex 為選配（接法見 README）；未選配時不另派 rescue，依 `rules/失敗分類與partial交接.md` Rule 3 停下向使用者回報兩次失敗的實際輸出。Codex 失敗一次即 fallback 回 `opus-executor`，不重試。

## Good Example

- 這個例子是好的，因為 rescue 是在兩次失敗且失敗證據已整理後才觸發，並附兩次失敗的證據派工。

````md
工單 #2：opus-lite-executor 失敗（測試 3 紅）→ opus-executor 失敗（同 3 紅，回報疑似 fixture 時區問題）
→ 已選配 Codex 時派 Codex rescue，工單附兩次失敗的實際輸出；未選配時停下向使用者回報。
````

## Bad Example

- 這個例子是壞的，因為它把 codex 當成第一順位 executor，不符合 rescue 只在 Claude executor 失敗兩次或需要異質視角時觸發的定位。

````md
這張工單看起來有點難，直接派 codex 做比較穩。
````

# Rule 6 - 平行判定與 worktree 使用條件

- Level: `SHOULD`
- 檔案或語意範圍重疊、或共用測試資源（DB、port、build output、cache）→ 序列執行；寫入與資源完全獨立才並行。
- 不用 worktree 的並行共用同一份 working tree：baseline 在全部發派前拍一次，Phase 4 compare 以所有並行工單允許檔的聯集比對，越界歸屬由 orchestrator 讀 diff 判定；歸屬不了就改序列。
- 一般工單不用 worktree。確實值得平行化的大型任務要用時，須先確認 worktree 基底（`worktree.baseRef`，預設是 origin/HEAD 不是目前 HEAD）並明定整合方式：誰 commit、變更如何帶回主樹、在哪跑最終驗收；說不清楚就改序列。

## Good Example

- 這個例子是好的，因為它用「共用資源」而非「檔案不同」判定，兩張工單雖不同檔仍序列。

````md
工單 #3（改 migration）與工單 #4（改 seed script）都會動同一個測試 DB → 序列。
工單 #5（純文件）與工單 #3 無共用資源 → 可並行。
````

## Bad Example

- 這個例子是壞的，因為它只看檔案清單不重疊就並行，兩個 executor 同時跑測試互相污染 DB。

````md
#3 與 #4 改的檔案不一樣，一起派。
````
