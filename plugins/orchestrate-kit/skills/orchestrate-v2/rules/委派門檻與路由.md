# Rule 1 - 診斷、切工單、驗收、仲裁、close 自己做，只有實作才委派

- Level: `SHOULD`
- orchestrator 負責最貴、最關鍵的判斷：診斷、切工單、驗收、仲裁、close；這些不發派。
- 除微小的黏合修改外，orchestrator 不親自寫 code；實作交給 executor。
- 需要頂級模型的只有診斷與仲裁，那是 orchestrator 自己做的事，不發派。

## Good Example

- 這個例子是好的，因為 orchestrator 自己完成診斷後才發派，發派的是實作而非判斷。

````md
診斷（自己做）：讀 `src/auth/*`，確認 token 續期邏輯只在 `refresh.ts` 一處；影響範圍兩檔。
發派：工單 #1 給 opus-lite-executor，改 `refresh.ts` 與其測試。
````

## Bad Example

- 這個例子是壞的，因為它把診斷外包給 subagent，orchestrator 拿到的是轉述而非自己讀 code 的判斷。

````md
Agent(general-purpose)：「幫我看看 auth 模組哪裡有問題，然後直接修好。」
````

# Rule 2 - 依難度路由 executor，model 與 effort 隨層級綁定

- Level: `SHOULD`
- 一般 coding 與機械型（範圍明確、單模組、中低複雜度；批次替換腳本、改名、單檔小修）→ `opus-lite-executor`（opus、low）。
- 高難度 coding（跨模組、concurrency／狀態機、需要深度推理）→ `opus-executor`（opus、high）。
- Phase 2 的 risk_signals 估算 `gate_hits` 非空（policy 所列路徑類 gate），或工單目標命中語意類 gate（core_business_rule 核心商業規則、concurrency／狀態機、data_safety 資料安全、cross_module_contract 跨模組介面）→ `opus-executor`，不看 diff 大小與其他判準。
- effort 寫在各 agent 定義檔，Agent tool 無法單次覆寫；要換強度就換層級。

## Good Example

- 這個例子是好的，因為它依難度特徵挑 executor，而不是一律派最強模型。

````md
工單 #1（改 DTO 欄位名、單檔、測試已覆蓋）→ opus-lite-executor
工單 #2（撮合引擎狀態機新增「部分成交」狀態，跨三個模組）→ opus-executor
工單 #3（只改兩個檔，risk_signals 估算 gate_hits 命中 migration）→ opus-executor
工單 #4（依替換表寫一支帶 count==1 斷言的腳本）→ opus-lite-executor
````

## Bad Example

- 這個例子是壞的，因為它把單檔改名也派 opus-executor，在不需深度推理的工作上花 high effort 的思考成本。

````md
所有工單一律 opus-executor，比較保險。
````

# Rule 3 - 搜尋與精讀派 `opus-lite-explorer`，路由用的自訂 agent 定義檔必宣告 model 與 effort

- Level: `SHOULD`
- 找檔案、追引用、精讀文件等唯讀工作派 `opus-lite-explorer`（opus、low），不派 Explore、general-purpose 等內建 agent。
- 內建 agent 沒有定義檔可宣告 effort，Agent tool 也沒有 effort 參數，實際會沿用 orchestrator 的 effort（subagent transcript 的每回合 effort 紀錄可查證）；無 model 行的 agent 也會繼承 orchestrator 的模型。
- 路由表內的自訂 agent（executor、explorer、reviewer）定義檔必宣告 `model` 與 `effort`。

## Good Example

- 這個例子是好的，因為唯讀搜尋派給定義檔已宣告 opus＋low 的 explorer。

````md
Agent(subagent_type: opus-lite-explorer)：「列出所有引用 `LegacyPricing` 的檔案。」
````

## Bad Example

- 這個例子是壞的，因為內建 Explore 帶了 model 也無法指定 effort，實際會跑 opus＋xhigh（沿用 orchestrator 的 effort），不是 low。

````md
Agent(subagent_type: Explore, model: opus)：「列出所有引用 `LegacyPricing` 的檔案。」
````

# Rule 4 - 發派前必有 baseline

- Level: `MUST`
- 任何 executor 寫入前，orchestrator 必須先執行 `scripts/baseline.py snapshot` 記錄 working tree（dirty、staged、untracked 與各檔 hash），並保留 manifest 路徑到驗收。
- 沒有 baseline 就發派，Phase 4 無法判定越界修改與使用者原有修改是否被覆蓋，驗收不成立。

## Good Example

- 這個例子是好的，因為 manifest 路徑被記下來，驗收時 compare 有基準。

````md
uv run "${CLAUDE_SKILL_DIR}/scripts/baseline.py" snapshot
→ baseline written: C:/Users/x/AppData/Local/Temp/claude-orchestrate/3f2a…/baseline-20260903T081500Z.json
（記入工單 #1 的「baseline manifest」欄）
````

## Bad Example

- 這個例子是壞的，因為 orchestrator 先發派再想到拍 baseline，這時 executor 可能已經寫入，基準已被污染。

````md
Agent(opus-lite-executor, 工單 #1) … 執行中
→ 「等一下先跑個 baseline」
````

# Rule 5 - Codex rescue 只在 Claude executor 失敗兩次或需要異質視角時觸發

- Level: `SHOULD`
- 觸發：Claude executor 同一工單失敗兩次、或明顯需要異質模型視角時，由 orchestrator 直接發派（不經 subagent）。
- 不作一般工單入口。
- Codex 為選配（接法見 README）；未選配時不另派 rescue，依 `rules/失敗分類與partial交接.md` Rule 3 停下向使用者回報兩次失敗的實際輸出。Codex 失敗一次即 fallback 回 `opus-executor`，不重試。

## Good Example

- 這個例子是好的，因為 rescue 是在兩次失敗且失敗證據已整理後才觸發，並附兩次失敗的證據派工。

````md
工單 #2：opus-lite-executor 失敗（測試 3 紅）→ opus-executor 失敗（同 3 紅，回報疑似 fixture 時區問題）
→ 已選配 Codex 時派 Codex rescue，工單附兩次失敗的實際輸出；未選配時停下向使用者回報。
````

## Bad Example

- 這個例子是壞的，因為它把 codex 當成第一順位 executor，燒掉稀缺額度。

````md
這張工單看起來有點難，直接派 codex 做比較穩。
````

# Rule 6 - 平行判定與 worktree 使用條件

- Level: `SHOULD`
- 檔案或語意範圍重疊、或共用測試資源（DB、port、build output、cache）→ 序列執行；寫入與資源完全獨立才並行。
- 不用 worktree 的並行共用同一份 working tree：baseline 在全部發派前拍一次，Phase 4 compare 以所有並行工單允許檔的聯集比對，越界歸屬由 orchestrator 讀 diff 判定；歸屬不了就改序列。
- 一般工單不用 worktree。確實值得平行化的大型任務要用時，須先確認 worktree 基底（`worktree.baseRef`，預設是 origin/HEAD 不是目前 HEAD）並明定整合方式：誰 commit、變更如何帶回主樹、在哪跑最終驗收；說不清楚就改序列。

## Good Example

- 這個例子是好的，因為它用「共用資源」而非「檔案不同」判定，兩張工單雖不同檔仍序列。

````md
工單 #3（改 migration）與工單 #4（改 seed script）都會動同一個測試 DB → 序列。
工單 #5（純文件）與工單 #3 無共用資源 → 可並行。
````

## Bad Example

- 這個例子是壞的，因為它只看檔案清單不重疊就並行，兩個 executor 同時跑測試互相污染 DB。

````md
#3 與 #4 改的檔案不一樣，一起派。
````
