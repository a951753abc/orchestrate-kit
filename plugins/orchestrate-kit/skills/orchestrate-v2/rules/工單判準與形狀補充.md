# Rule 1 - 工單只約束結果與邊界，不約束實作方法

- Level: `SHOULD`
- 工單不含可直接照抄的完整實作 code；除非順序涉及安全或資料完整性，不寫死實作步驟。
- 工單要低熵：executor 不應需要猜根因、猜驗收標準、猜產品意圖；executor 需要猜，表示工單切壞了，退回 orchestrator 重切。
- spec 與驗收優先引用實存的 code（既有測試、參考實作、mockup 檔）；散文描述只在沒有可引用實體時退而求其次。
- 驗收指令應可判定，並逐條標執行時點：需要修改前結果的項目（問題重現：修改前應失敗；比較基準：既有失敗數、數值基準）標「修改前要跑」，新增檔案、新功能的測試這類修改前跑不出意義的項目標「只在修改後跑」。「修改前」指改動被測程式之前，工單要求新增的測試與 fixture 可先寫好再跑。修改前的試跑由 executor 執行，跑不出可判定結果時 executor 停止並回報，orchestrator 回 Phase 2 改寫該工單。
- 驗收的測試範圍選本工單改動影響到的部分（專案有依改動挑測試的工具就用它）；整個交付範圍的全套只排在最後一張一般工單，修正工單回到受影響範圍。只有改測試機制本身（fixture、runner、清理與等待）才要求多輪全套與故障注入。專案規範另有執行範圍規定時以專案為準。
- 允許修改的檔案清單應註明預期的 generated artifacts（lockfile、snapshot、migration 等）、是否允許新增檔案、是否允許安裝套件；這三項註明與固定禁止事項由 `templates/work-order.md` 預填。清單外禁區的約束以 Rule 2 為唯一居所。
- 工單填「使用情境」（誰在用、什麼環境、資料可否重建、誰負責復原；review focus 沿用）與「證據檔目錄」（放 repo 外，executor 寫入 `before-<驗收編號>.txt`、`after-<驗收編號>.txt`），兩者由 `templates/work-order.md` 預留欄位。

## Good Example

- 這個例子是好的，因為它用實存測試檔定義驗收，只給邊界與結果，實作方法留給 executor。

````md
## 目標
`OrderService.cancel()` 在訂單已出貨時拒絕取消並回傳 `ORDER_SHIPPED`。

## 驗收條件
- V1（修改前要跑）：`npm test -- tests/order/cancel.spec.ts`，修改前新增情境失敗、修改後全綠；新增情境對照既有的 `describe('cancel')` 寫法
- V2（只在修改後跑）：`npm run typecheck` exit 0
````

## Bad Example

- 這個例子是壞的，因為它把完整實作貼進工單並寫死步驟，executor 只剩照抄，orchestrator 反而替 executor 承擔了實作正確性。

````md
## 目標
照下面的 code 改 `OrderService.cancel()`：
```ts
if (order.status === 'shipped') { throw new DomainError('ORDER_SHIPPED') }
```
步驟：1. 先開 order.service.ts；2. 在第 42 行插入；3. 存檔後跑測試。
````

# Rule 2 - 清單外檔案與 git 寫入操作未經工單明示授權一律禁止，commit 只依使用者指示

- Level: `MUST`
- 工單的禁止事項必含 `templates/work-order.md` 預填的固定三條（清單外禁區、git 寫入禁令、不順手重構）；填單時不得刪除或放鬆，例外只能以工單內明示授權的形式出現。
- orchestrator 自己也不擅自 commit；commit 的授權來源只有使用者指示。已定案的連續工單之間驗證全綠＋證據落檔後直接接下一張，不 commit 也不請示；使用者已明示逐張驗收後 commit 時，才在每張驗收後 commit 並改以 commit 為單位回報。

## Good Example

- 這個例子是好的，因為禁止事項把 git 禁令寫成固定文字，且允許清單之外的需求以「停止並回報」處理。

````md
## 允許修改的檔案
- `src/order/order.service.ts`
- `tests/order/cancel.spec.ts`
（可新增檔案：否；可安裝套件：否；預期 generated artifacts：無）

## 禁止事項
- 不順手重構、不擴 scope、不放鬆既有 gate
- git 寫入操作（add／commit／reset／checkout／restore／clean／stash）一律禁止；需要動清單外的檔案時停止並回報
````

## Bad Example

- 這個例子是壞的，因為工單默許 executor「順手 commit」，orchestrator 在驗收前就失去比對 working tree 的基準，也繞過了使用者的 commit 授權。

````md
## 禁止事項
- 不順手重構
- 改完可以直接 commit，訊息自己寫
````

# Rule 3 - 工單要求新增或修改測試時，一併寫入兩條測試品質約束

- Level: `SHOULD`
- 期望值必須來自獨立來源（已知字面值、規格算例）；不得用與實作同邏輯重算出期望值，否則是恆真測試。
- 測試只落在工單指明的公開介面縫（seam）上，不斷言內部實作細節：不 mock 內部協作者、不驗證呼叫次數與順序。
- 兩條約束由 `templates/work-order.md`「測試品質約束」段預填，工單只需填入 seam 名稱。

## Good Example

- 這個例子是好的，因為期望值是規格給的字面值，斷言落在公開回傳值上。

````md
## 驗收條件
- 新增 `tests/pricing/discount.spec.ts`：輸入 `{ subtotal: 1000, tier: 'gold' }` 期望 `850`（規格 §3.2 算例）
- 測試品質約束：期望值不得由 `applyDiscount()` 重算；只斷言 `applyDiscount()` 回傳值，不 mock `TierRepository`
````

## Bad Example

- 這個例子是壞的，因為期望值由同一段實作邏輯算出，且斷言的是內部協作者被呼叫的次數。

````md
- 測試：`expect(applyDiscount(input)).toBe(input.subtotal * TIER_RATE[input.tier])`
- 並確認 `tierRepo.find` 被呼叫恰好一次
````

# Rule 4 - Bug 工單的驗收加項

- Level: `SHOULD`
- 驗收應含：修正前的失敗證據（標「修改前要跑」，由 executor 在修改前執行）；regression test 修正前失敗、修正後通過（不適用時說明理由與替代驗證；flaky 修復以連跑 N 次全綠為證據）；原始症狀的直接驗證；相關 test suite／typecheck／build。
- 修正前的失敗訊息須是預期的差異（狀態碼、欄位值、筆數不符）；失敗原因是 schema 缺欄位、路由不存在或例外時，代表 assertion 還沒被執行到，不算失敗證據，先補到測試紅在 assertion。
- 可在目標後附「診斷依據：<已觀察事實、根因證據、已排除假說>」，但不得把未驗證 hypothesis 寫成 executor 必須服從的結論。
- 失敗證據可直接引用 Phase 1 取得的紀錄，不必重新描述。

## Good Example

- 這個例子是好的，因為診斷依據區分了已觀察事實與已排除假說，驗收含修正前後的 regression test 對照。

````md
## 目標
修正 `parseCsv()` 遇到 BOM 開頭檔案時首欄名帶 `﻿` 的問題。
診斷依據：`tests/fixtures/bom.csv` 重現 100%；`hexdump` 確認前三 byte 為 EF BB BF；已排除「編碼設定」假說（`encoding: 'utf8'` 已是預設）。

## 驗收條件
- 新增 `tests/csv/bom.spec.ts`，修正前執行必須失敗（貼輸出），修正後通過
- `node scripts/import.js tests/fixtures/bom.csv` 首欄名為 `id`（原始症狀）
- `npm test` 全綠
````

## Bad Example

- 這個例子是壞的，因為它把未驗證的猜測寫成結論，且驗收只有「測試通過」，沒有修正前失敗證據與原始症狀驗證。

````md
## 目標
應該是 `readFile` 沒指定編碼造成的，改成 utf8 就好。

## 驗收條件
- 測試通過
````

# Rule 5 - 最佳化形工單的驗收加項

- Level: `SHOULD`
- 演算法／效能／SQL／交易策略類：先有明顯正確的 reference／baseline 與測試；驗收應含與 reference 在代表性輸入、邊界條件與隨機案例上的結果比對；效能宣稱應附 benchmark 證據。
- 資料遷移類改為遷移前後不變式檢查：筆數、checksum、抽樣比對。

## Good Example

- 這個例子是好的，因為它保留了明顯正確的 reference 實作作為對照，隨機案例與 benchmark 都有明確產物。

````md
## 驗收條件
- `tests/match/engine.spec.ts` 新增 property test：1000 組隨機訂單簿，`fastMatch()` 與 `referenceMatch()`（現有實作，保留不刪）結果逐筆相等
- 邊界：空訂單簿、單邊、價格相同時間不同
- `npm run bench:match` 輸出 p50 延遲，附修改前後兩次數字
````

## Bad Example

- 這個例子是壞的，因為它讓 executor 同時改掉唯一的對照實作，效能宣稱也沒有可比對的數字。

````md
## 目標
把 `match()` 改快一點，順便把舊的實作刪掉。

## 驗收條件
- 測試通過，感覺變快就好
````

# Rule 6 - 批次編輯形工單改為替換表加腳本，不派 executor 逐檔改

- Level: `SHOULD`
- 修正項 ≥10 處且能寫成「檔:行:前→後」表（終審仲裁、詞彙統一、時點標籤更新）時：orchestrator 產替換表，派一張 `opus-lite-executor` 工單寫一支帶 `count==1` 斷言的腳本一次跑完。
- executor 逐檔 Read／Edit 上百回合＝工單切壞，退回重切。

## Good Example

- 這個例子是好的，因為工單交付的是替換表與腳本，每一處替換都有 `count==1` 斷言防止漏改或重複改；腳本只在「一次性操作」段執行一次，驗收條件只留可重跑的結果檢查。

````md
## 目標
依附表把 14 處「發佈」統一為「發布」。

## 允許修改的檔案
- `scripts/replace_terms.py`（新增）
- 附表所列 6 個 `.md` 檔

## 一次性操作
- `python scripts/replace_terms.py` 執行一次，對附表每列斷言替換前 `count==1`，全部成功後 exit 0，輸出寫進證據檔

## 驗收條件
- V1（只在修改後跑）：`rg 發佈 docs/` 無結果
- V2（修改前要跑）：`rg -c 發布 docs/` 合計，修改後比修改前多 14
````

## Bad Example

- 這個例子是壞的，因為它是 2026-08-27 的實際事故：73 處替換派給 3 個 executor 逐檔 Edit，燒掉該 session 兩個 5h limit。

````md
## 目標
依終審仲裁結果修正 docs/ 下所有詞彙不一致處（73 處）。

## 驗收條件
- 逐檔確認都改好了
````

# Rule 7 - 唯讀頁面／純 UI 形工單以瀏覽器可觀察結果為驗收

- Level: `SHOULD`
- 適用範圍以 risk-grade `rules/硬性gate與safe-change白名單.md` Rule 2 的「唯讀 UI 形狀」定義為準，本檔不另行定義。
- 驗收條件寫成瀏覽器可觀察的結果（頁面、元素、操作後畫面），並在工單標注「唯讀 UI」供 risk-grade 判為 safe-change。
- 只要工單同時碰到寫入路徑、授權或資料語意，就不屬本形狀，回到一般工單處理。

## Good Example

- 這個例子是好的，因為驗收是瀏覽器可觀察的具體結果，且工單明確標注形狀。

````md
## 目標（唯讀 UI）
訂單列表頁加「出貨日」欄位並支援排序。

## 驗收條件
- 開 `/orders`，表頭出現「出貨日」，點擊後列表依日期遞增／遞減切換（截圖）
- `npm run typecheck` exit 0
````

## Bad Example

- 這個例子是壞的，因為它把「純 UI」當成不用驗收的理由，也沒有標注形狀，risk-grade 無法據此判為 safe-change。

````md
## 目標
列表頁加個欄位。

## 驗收條件
- 看起來正常就好
````

# Rule 8 - 原始碼文字解析形工單的驗收加項

- Level: `SHOULD`
- 適用：工單改動的程式以 regex 或 heuristic 從原始碼（樣板、controller、JS、設定檔）抽取事實，供下游產生器或報表使用；新增規則與修改既有規則都算。
- 驗收條件除 golden 比對外，逐類列出邊界變體，每類至少一個 fixture 案例；該類不會發生時寫「不適用：<理由>」；每個變體要能在對應規則改回舊寫法（mutant）時變紅，期望值依 Rule 3 取自 fixture 的字面內容。七類：
  1. 字面值內含分隔符：引號內出現結尾標記、括號、分號（`?>`、`]`、`{`、`;`）或另一種引號。
  2. 註解：行內註解、整行註解、docblock 內出現與規則同形的文字。
  3. 多行與同行鏈式：一個語句拆多行寫；同一行後面鏈了另一個呼叫。
  4. 串接動態值：字面值收尾後接 `+`、`.` 或變數，靜態列舉不出 → 判不可解析並留旗標，不猜。
  5. 識別字撞名：目標識別字是另一個識別字的前綴或後綴 → 整詞比對。
  6. 輸入契約型別：上游 JSON 的鍵為 null、非字串、float 或 bool 當整數傳入、list 與 dict 互換 → 退回未解析路徑，不 traceback。
  7. 負向路徑的正向斷言：不命中規則的輸入仍產出既有結果，守門不得把普通路徑一起關掉。
- 解析不出的輸入一律落到「未解析＋旗標或 TODO」路徑；工單不得要求解析器補猜。

## Good Example

- 這個例子是好的，因為七類邊界各有 fixture 或明寫不適用與理由，每個變體都附 mutant 會紅的證據，解析不出的走旗標。

````md
## 目標
`extract_sites.py` 從樣板檔抽出 `$.get('/<module>/<page>/datatable/<param>/<value>')` 站點，寫進事實表的 `embedded_in`。

## 驗收條件
- `uv run scripts/tests/extract_sites/check.py` 全綠，fixture 逐類對應：
  - 分隔符：`quotes.phtml`（value 內含另一種引號、樣板碼 `<?= … ?>` 內的 `/`）
  - 註解：`commented.phtml`（整行註解掉的舊站點不算）；行尾註解不適用：站點行不會帶行尾註解，列入已知限制
  - 多行／鏈式：`multiline.phtml`（呼叫引數分三行）
  - 串接：`concat.phtml`（收尾引號後接 `+ mode` → 該筆 null＋旗標 `SITE_UNRESOLVED`）
  - 撞名：`page` 為 `note` 時不得命中 `note.file` 的站點
  - 型別：不適用：輸入是原始碼，`embedded_in` 的型別守門屬消費端 `gen_scaffold` 的工單
  - 正向：沒有站點的 `plain.phtml` 仍產出其餘欄位
- 每個變體把對應規則改回舊寫法時該變體必須紅（貼一次輸出）
````

## Bad Example

- 這個例子是壞的，因為只驗收正常站點解析成功，引號、多行、串接、撞名、型別全靠 review 事後補，每補一類就多一輪修正與 review。

````md
## 目標
從樣板檔抽出 datatable 站點。

## 驗收條件
- 新 fixture 的站點解析出 `param`／`value`
- check.py 全綠
````

# Rule 9 - 突變驗證的還原步驟一律更新 mtime 並比對雜湊

- Level: `SHOULD`
- 適用：驗收條件含「改壞程式碼→確認測試變紅→還原」的突變驗證（含 Rule 8 的 mutant），不分語言；orchestrator 在 Phase 4 自己重跑突變時同樣適用。
- 還原順序固定寫成：以備份覆蓋回去 → 更新 mtime → SHA-256 與突變前比對一致 → 刪備份。PowerShell `Copy-Item`、`mv`、`os.replace` 還原都會帶回較舊的 mtime，cargo 增量編譯與 PHP opcache 以 mtime 判斷檔案是否變動，會沿用突變版的編譯結果。

## Good Example

- 這個例子是好的，因為還原後先更新 mtime，再以雜湊確認內容回到突變前，最後的綠燈確實來自原始程式碼。

````md
## 驗收條件
- 突變驗證：備份 `src/scan.rs` → 把 `>=` 改成 `>` → `cargo test --test scan` 必須紅（貼輸出）→ 以備份覆蓋回去 → `(Get-Item src/scan.rs).LastWriteTime = Get-Date` → `Get-FileHash -Algorithm SHA256` 與突變前一致 → 刪備份 → `cargo test --test scan` 全綠
````

## Bad Example

- 這個例子是壞的，因為它是 2026-09-24 的實際事故：還原步驟沒有更新 mtime，cargo 判定來源沒變，全套測試 0.07 秒就結束並顯示突變版的紅燈，差點被誤判為回歸失敗。

````md
## 驗收條件
- 突變驗證：備份 → 改壞 → 測試紅 → `Copy-Item` 以備份覆蓋回去 → 測試綠
````

# Rule 10 - 一次性修改操作與結果檢查分開寫，驗收不原樣重跑操作

- Level: `SHOULD`
- 適用：替換腳本、migration、資料匯入、批次改檔這類執行一次就改變狀態、再跑一次結果不同的操作。
- 工單把操作寫進「一次性操作」段，由 executor 執行一次並把輸出寫進證據檔目錄的 `after-op.txt`；驗收條件寫成操作後可重跑而不改變狀態的結果檢查：內容、數量、diff。
- 操作部分失敗時依 `rules/失敗分類與partial交接.md` Rule 2 附狀態交接或還原後重發，不原樣重跑操作。

## Good Example

- 這個例子是好的，因為操作只執行一次並留下輸出，驗收條件全是重跑也不改變狀態的結果檢查。

````md
## 一次性操作
- `python scripts/replace_terms.py` 執行一次，對附表每列斷言替換前 `count==1`，輸出寫進 `after-op.txt`

## 驗收條件
````
