# Rule 1 - 會影響產品行為、架構或修法的假設分成三類，各有歸屬

- Level: `SHOULD`
- 已有證據支持：code、測試輸出、文件或使用者先前裁決可直接佐證；寫明證據出處即可開工單。
- 尚待驗證：能用重現、對照實驗或量測分辨真假的技術假說，歸 `orchestrate-kit:debug-by-evidence` skill 取證，不進工單當前提；不能實驗、也不需使用者裁決的純技術細節，帶進工單並在「診斷依據」標明為假設（見 Rule 3）。
- 必須由使用者裁決：產品行為的取捨、商業判斷、風險接受、不可逆操作、會產生費用的外部 AI API 呼叫。不問的：有既定慣例的技術實作、可從 code 或文件查證的事實、可逆且明顯符合請求方向的決定、已定案連續工單之間的開工。
- 問的時候先用 2～4 句白話重建脈絡（在處理哪個功能、先前裁了什麼、這題決定什麼），給選項與推薦，選項標籤用日常語言、內部代號放說明文字；不開放式丟回去。
- 假設不明列就開工單，executor 會用猜的；executor 需要猜表示工單切壞了。

## Good Example

- 這個例子是好的，因為每個假設都標了類別與歸屬，只有第三類停下來問。

````md
假設清單：
A1 已有證據：續期邏輯只在 refresh.ts（rg 結果 1 處）
A2 尚待驗證：token 過期是時區問題 → 先用固定時區重跑測試（orchestrate-kit:debug-by-evidence）
A3 須使用者裁決：過期後是靜默續期還是強制重登 → 問，推薦靜默續期並記 audit log
````

## Bad Example

- 這個例子是壞的，因為它把三種假設混成一句，直接當成工單前提。

````md
應該是時區問題，過期後就靜默續期，工單照這樣切。
````

# Rule 2 - spec、code、tests 或既有行為互相矛盾時不自行選邊

- Level: `SHOULD`
- 發現矛盾先回報衝突點與各選項的影響（哪些行為會變、哪些測試會改），不挑一邊寫進工單。
- 「以測試為準」「以 code 為準」都是選邊；只有使用者先前已裁決的例外可以直接引用。

## Good Example

- 這個例子是好的，因為它把矛盾與兩個選項的後果攤開，交使用者裁。

````md
衝突：SPEC §3.2 說退款上限為原付款金額；tests/refund.spec.ts 允許超額退款（手續費補償）
選項 A 依 SPEC：改測試，補償改走另一流程
選項 B 依測試：改 SPEC，退款上限加手續費
影響：A 動 1 個測試；B 動 SPEC 與 2 個算例
````

## Bad Example

- 這個例子是壞的，因為它靜默選了測試那一邊，使用者事後才發現 SPEC 被改。

````md
測試已經這樣寫了，SPEC 應該是舊的，照測試改。
````

# Rule 3 - 涉及產品行為、架構、資料安全、成本或不可逆決策的未決假設，釐清後才開實作工單

- Level: `SHOULD`
- 這五類假設未決時不開實作工單；可以先開取證或探索類的唯讀工單。
- 其餘未決假設（純技術實作細節）可以帶著假設開工單，但要在工單「診斷依據」寫明它是假設而非結論。

## Good Example

- 這個例子是好的，因為它把資料安全類的假設擋在工單之前，技術細節假設則帶著走。

````md
未決：刪除帳號是否連帶清除訂單歷史（資料安全）→ 先問，不開工單
未決：用 soft delete 還是 archive table（技術細節）→ 工單診斷依據標「假設採 soft delete，executor 發現不可行時回報」
````

## Bad Example

- 這個例子是壞的，因為它把不可逆的資料刪除決策當成技術細節帶進工單。

````md
工單：實作刪除帳號，連帶清除訂單歷史（假設使用者要這樣）
````
