# Rule 1 - 裁量以 blast radius 與可逆性為主軸

- Level: `SHOULD`
- 核心問題只有一個：「這個改動在 production 出錯時，哪些使用者可見的行為會壞？」
- blast radius：被改動的函式或模組有多少呼叫者、是否為共用模組、是否在熱路徑、是否影響多租戶。
- 可逆性：revert 是否即可恢復；涉及資料寫入、外部副作用（寄信、扣款、推播）、不可撤回的訊息 → 低可逆。
- 高 blast radius 或低可逆 → 中高；兩者皆低 → 可考慮低，再看 Rule 2。

## Good Example

- 這個例子是好的，因為它把影響範圍追到具體呼叫者，並以可逆性定案。

````md
變更：utils/format_date() 改輸出格式
blast radius：rg 找到 14 個呼叫點，含匯出報表與寄信模板
可逆性：revert 即恢復，但已寄出的信不可撤回
判定：中高（裁量層）——低可逆的外部副作用
````

## Bad Example

- 這個例子是壞的，因為它沒有追呼叫者就下結論。

````md
變更：utils/format_date() 改輸出格式
判定：低，只是個工具函式
````

# Rule 2 - 測試覆蓋只能在 blast radius 低時作為降級理由

- Level: `SHOULD`
- 凍結測試或既有測試完整覆蓋、且斷言落在公開介面上，可作為判低的理由，前提是 Rule 1 未判中高。
- 「完整覆蓋」要對照 diff 的分支與工單驗收指令逐一確認，不憑測試檔存在就認定。
- 測試本身被改動（放鬆斷言、刪案例）不算覆蓋，反而是升級訊號。

## Good Example

- 這個例子是好的，因為它逐分支對照測試，才拿覆蓋當降級理由。

````md
變更：parse_csv() 加 BOM 去除（+1 行）
blast radius：3 個呼叫者，皆為匯入流程；revert 即恢復
測試：tests/csv/bom.spec.ts 覆蓋有 BOM、無 BOM 兩分支，斷言在 parse_csv() 回傳值
判定：低（裁量層）
````

## Bad Example

- 這個例子是壞的，因為 diff 同時放鬆了測試斷言，卻仍把「測試通過」當降級理由。

````md
變更：utils/slugify() 換演算法；tests/slugify.spec.ts 把 toBe('a-b') 改成 toMatch(/a/)
判定：低，測試都過了
````

# Rule 3 - 大小只影響分批建議，不影響等級

- Level: `SHOULD`
- 變更行數超過 policy `attention_limit_lines` → 建議 review 時分批（每批 ≤20 檔）或拆工單；不因此升級。
- 反向同樣成立：小 diff 不因此降級（12 行的 migration 在大表上加 index 可以鎖表）。
- 結構複雜度（分支數、狀態轉移、巢狀條件）比行數更能代表風險，裁量時看複雜度不看行數。

## Good Example

- 這個例子是好的，因為它把大小與風險分開處理。

````md
變更：IDE 重構把 OrderSvc 改名為 OrderService（3,000 行、42 檔，行為不變，typecheck 與全部測試綠）
判定：低（safe 層：typecheck／tests 完整涵蓋的機械修改）；行數超過 attention_limit → review 分三批
````

## Bad Example

- 這個例子是壞的，因為它用行數當風險訊號，兩個方向都錯。

````md
3,000 行 → 中高；12 行 migration → 低
````

# Rule 4 - 裁量理由必須可追溯到具體檔案與行為

- Level: `SHOULD`
- 理由寫成「哪個檔案的哪個行為，出錯時影響什麼」，不寫「感覺風險不高」「改動很單純」。
- 理由要能讓校準時的讀者不重看 diff 就理解當時為何這樣判。

## Good Example

- 這個例子是好的，因為理由指向具體檔案、行為與影響。

````md
理由：src/order/cancel.ts 新增已出貨檢查，只影響取消路徑；失敗時使用者看到錯誤訊息而非靜默成功，revert 即恢復
````

## Bad Example

- 這個例子是壞的，因為理由無法追溯。

````md
理由：改動很小，應該沒問題
````
