# Rule 1 - 校準看等級與結果的對照，不看單場感受

- Level: `SHOULD`
- 以 risk-grade 的 `risk_ledger.py summary` 四象限為依據：
  - 中高＋有實質 findings：正確升級
  - 中高＋連續無 findings：過度升級候選，檢查是哪個 gate 或裁量理由造成
  - 低＋事後發現問題或事故：漏網，代表缺訊號，補 gate 或收緊白名單
  - 低＋無問題：正確
- 單場「這次派 review 好像白派了」不構成校準依據；至少累積一個象限有重複樣本才動 policy。

## Good Example

- 這個例子是好的，因為它從對照表找出重複型態，再定位到具體 gate。

````md
summary：中高 9 筆，其中 4 筆無 findings，全部命中 audit_logging gate 且變更只在 monitoring/dashboards/*.json
結論：audit_logging gate 過寬，dashboard 定義檔應排除
````

## Bad Example

- 這個例子是壞的，因為它憑單場經驗改 policy。

````md
這次 audit_logging 的 review 沒找到東西，把 audit_logging gate 拿掉。
````

# Rule 2 - 修 gate 措辭，不加性質例外

- Level: `SHOULD`
- 過度升級的處置是把 gate 條件寫精確（縮路徑、加 `exclude`、把語意描述具體化），不是加「命中 gate 但測試覆蓋就降級」這類性質例外；性質例外會侵蝕 gate 的下限語意。
- 漏網的處置是補 gate 或把白名單類別收窄，不是把裁量層的閾值整體調高。

## Good Example

- 這個例子是好的，因為它是 Unblocked 公開的實際校準紀錄（2026 年 blog，出處列於設計文件 2026-09-03 修訂的研究附記）：policy 寫「ALTER」導致 `ALTER TABLE … ADD COLUMN`（可為 NULL、無預設、可 rollback）被判最高風險，修法是把準則改精確。

````md
原措辭：migrations that DROP, ALTER, or RENAME tables/columns
新措辭：migrations that DROP or RENAME tables/columns, ALTER a column type, or add a NOT NULL column without a default
````

## Bad Example

- 這個例子是壞的，因為它用性質例外解決過寬的 gate，之後任何 migration 只要附測試都能繞過。

````md
migration gate 維持「ALTER」，另加一條：有測試覆蓋的 migration 降為低。
````

# Rule 3 - 校準產出是 policy 修改提案，交使用者裁決後才改

- Level: `SHOULD`
- 提案內容：對應的 ledger id、現行措辭、建議措辭、預期影響（哪些歷史紀錄的等級會改變）。
- 新 gate 或放寬的閾值先以 advisory 方式跑一段期間，對照人類判斷後再啟用。
- policy 檔本身命中 `approval_governance` gate，修改一律經人審。

## Good Example

- 這個例子是好的，因為提案可追溯、可預估影響，且不直接改檔。

````md
提案：audit_logging gate 加 exclude ["**/monitoring/dashboards/**"]
依據：rg-…-a1b2、rg-…-c3d4、rg-…-e5f6、rg-…-g7h8（4 筆中高無 findings，皆只動 dashboard JSON）
預期影響：這 4 筆重跑會落到裁量層（JSON 不在白名單），由 blast radius 判定，預期為低
````

## Bad Example

- 這個例子是壞的，因為校準直接改了 policy，沒有留下依據與影響評估。

````md
已把 audit_logging gate 的 exclude 加上 dashboards，下次生效。
````
